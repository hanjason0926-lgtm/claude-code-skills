# 儀表板需求風險盤點

使用者手上有一組儀表板需求（可能是原型、需求文件、幾張圖的描述，或只有一句「我想做一個 X 儀表板」），要在動工前把坑找出來。

你的產出不是資料表設計，也不是「這樣做比較好」的建議。是三件事：

1. **哪些數字根本做不出來**（來源沒有那個東西）
2. **哪些會算錯但不會報錯**（口徑問題，數字看起來很正常）
3. **哪些現在不問就永遠補不回來**（資料沒開始記，事後無法回溯）

---

## 心法一：從來源往前推，不要從畫面往回推

大部分人分析儀表板需求時，是看著畫面問「這張圖要什麼資料」。這叫畫面驅動，它會漏掉最嚴重的問題。

因為畫面上的東西**看起來永遠都做得出來**。原型裡的假資料不會告訴你來源系統其實沒存那個欄位。

改成問：**來源系統實際長什麼樣？它記了什麼、沒記什麼、什麼時候記、會不會被改掉？**

兩者的差別在後果的量級：

| | 畫面驅動找到的問題 | 來源驅動找到的問題 |
|---|---|---|
| 典型 | 這張圖要不要預先算好、要不要拆表 | 退貨能不能追回原始明細 |
| 答錯 | 慢、或數字被誤讀 | **整個功能做不出來** |
| 何時能補救 | 隨時 | **很多是現在不問就永遠沒有** |

實務上最省力的第一步：**不要用問的，先要一份來源系統的 schema 加每張表 100 到 200 列樣本資料。** 下面一半的問題可以自己看出來，剩下的再問，而且問的時候可以指著具體欄位問，不會雞同鴨講。

## 心法二：先問能不能，再問會不會錯，最後才問快不快

排序永遠是這個：

```
能不能做  →  會不會算錯  →  快不快
（來源決定）  （口徑決定）   （工程可事後優化）
```

效能是最後才輪到的問題，而且幾乎都能事後解決。把力氣放在效能上而漏掉來源限制，是最常見的分析失誤。

## 心法三：優先標出「錯過就沒了」

有一類問題的特殊之處是**時間不可逆**：資料現在沒開始記，事後任何工程手段都補不回來。

典型例子：
- 搜尋沒有記錄「回傳幾筆結果」→ 零結果搜尋永遠算不出來
- 點數過期沒有寫流水 → 「多少點白白過期」永遠是零
- 行為事件只留 30 天而 ETL 停了 45 天 → 那段永遠是空的
- 訂單明細沒存下單當時的分類 → 商品移類後歷史歸屬永遠對不回去

這類項目要單獨標出來放在最前面，因為它們的決策成本會隨時間指數上升。

## 六個放大鏡

拿到任何一組儀表板需求，用這六個角度掃一遍。它們彼此獨立，而且幾乎涵蓋所有會出事的地方。

### 鏡 1：可加性

對每一個數字問：**這個東西跨時間、跨維度直接相加會不會錯？**

| 類型 | 例子 | 怎麼處理 |
|---|---|---|
| **可加** | 金額、件數、次數、人次 | 隨便加，適合先算好存起來 |
| **比率** | 客單價、轉換率、平均天數、使用率 | **只存分子與分母，不要存比率**。存了比率再平均，樣本大小不同的期間會被當成等重 |
| **不可加** | 人數、去重的任何東西 | 只能從最細的明細現算。任何聚合表出現「人數」欄位就是設計錯誤 |

**不可加是最常被忽略的一類，而且它的錯誤完全靜默。**

一個人 30 天內天天來，用每日人數相加會被算 30 次。結果可能出現「近 30 日不重複人數 8.2 萬」而全公司只有 7 萬人。不會報錯、不會當機，數字看起來很正常。

判斷技巧：**任何名字裡有「不重複」「幾個人」「幾位」「distinct」的東西都不可加。** 而且比率的分子或分母只要有一個不可加，整個比率就不能預先算好。

### 鏡 2：主體是「事」還是「人」

| 主體 | 特性 |
|---|---|
| **事**（訂單、異動、事件） | 發生了就定了，可以先算好、可以預聚合 |
| **人** | 會重複、身分會變、而且是**個資** |

主體是人的時候，多問三件事：

- **識別碼會不會變？** 離職再回任、轉調、系統移轉都可能重編。變了就會把同一個人算成兩個人，而且靜默。要找的是「永遠不變的人員唯一碼」，不是「員工編號」
- **同一個人會不會有多個身分？** 多裝置、未登入 vs 登入
- **個資治理怎麼要求？** 保留多久、誰能查、要不要最小顯示門檻（某分組只有 3 個人時顯示出來等於指名道姓）

### 鏡 3：時間歸屬

同一件事有很多個時間，儀表板要用哪一個？

```
事件發生時間  ≠  資料寫入時間  ≠  業務歸屬時間
```

具體要問：

- **退貨、退款、沖銷要記在原始交易日還是發生日？** 記回原始日 → 歷史數字會變動，要有可修訂窗與封帳；記在發生日 → 歷史凍結，但看不出「這批貨最後退了多少」
- **批次作業的時間戳是執行時間還是歸屬期間？** 例：8/1 凌晨跑 7 月的月結配發。記在 8/1 的話，趨勢圖每月一號會出現一根尖刺，而且 7 月的數字是零。這種問題**每個月固定發生一次**
- **有沒有補登？** 三個月前的單今天才進系統
- **有沒有關帳？** 有的話關帳後保證不動，可以安全封存與永久快取；沒有的話任何歷史都可能被改，只能定期全量對帳
- **跨日怎麼切？** 有夜班或跨時區的組織，自然日切分會把同一個班次的行為切成兩天

### 鏡 4：關聯完整性

把資料的層級畫出來，逐條確認**每一層能不能追溯到上一層**。斷掉一條就少一整組功能。

以交易類為例：

```
主檔 ──── 明細              ① 明細有沒有主檔 ID
沖銷主檔 ─ 沖銷明細          ② 沖銷明細有沒有沖銷主檔 ID
   └────── 原始主檔          ③ 沖銷能不能追回原單
           原始明細          ④ 沖銷明細能不能追回原明細
```

**第 ④ 條最容易斷也最致命。** 很多系統的退貨只記到訂單層級，不記是退了哪一行 → 退貨的商品與分類歸屬直接做不出來，所有退貨排行報廢。

同一個結構也適用於點數（異動能不能對到訂單、對到批次）、行為（事件能不能對到人、對到 session）。

### 鏡 5：資料生命週期

- **會不會被實體刪除？** 有 hard delete 的話，增量 ETL 永遠抓不到，已經算進去的數字會一直掛著。只能定期全量比對，或要求來源加刪除紀錄
- **會不會被修改？改多久以前的？** 決定重算範圍
- **有沒有可靠的異動時間欄位？誰維護的？** 應用層維護的話一定有繞過的路徑（DBA 手改、舊批次腳本），增量會靜默漏抓
- **來源保留多久？** 特別注意行為類資料。它常常是唯一「錯過就沒了」的資料，所以它的 ETL 監控要比其他更嚴

### 鏡 6：口徑衝突

這一鏡是掃畫面本身，找互相打架的地方。四種典型：

**同名不同義**
同一個名字在同一頁出現兩次但算法不同。例如一個是「本期發行」一個是「年度累計發行」，數量級差好幾倍並排在一起。使用者無法判斷該引用哪一個。

**母體不一致**
兩張並排的圖，一個在數「筆」一個在數「人」，長得一模一樣。使用者一定會拿來互相推算，然後推錯。

**區間長度改變指標語意**
累計型的分佈圖（消費金額分層、購買頻次分層）會隨區間拉長整個往右塌。查一年的話所有人都落在最高一格，圖就廢了。要嘛固定觀察窗，要嘛在圖上標明。

**前期比較的隱形成本**
每張 KPI 卡都有「vs 前期」的話，每次查詢實際上要查兩個區間。這會讓資料保留期的需求直接翻倍：能查一年，就要留兩年。

## 工作流程

### 第一步：把畫面元素列出來

不要憑印象分析。先把每一個 KPI 卡與每一張圖列成清單。如果有原型檔案就實際打開讀，不要只看描述。

**如果使用者只給了一句話（「我想做一個銷售儀表板」），先幫他把典型元素列出來再往下走。** 沒有具體元素就沒辦法做具體盤點，泛泛而談的 BI 建議沒有價值。

### 第二步：對每個元素標可加性

用鏡 1 的三分類逐一標記。這一步會自然浮出最難的幾個元素——通常是那些分子或分母有「人數」的。

### 第三步：跑來源盤點題庫

依資料的類型套用對應的題目。完整題庫見 `references/question-bank.md`，依「交易類 / 沖銷類 / 行為類 / 帳務點數類 / 主檔類 / 時間與關帳」分組。

不要整份倒給使用者。挑跟他的畫面真正相關的，而且要說明**答錯會怎樣**——沒有後果說明的問題清單，對方不知道為什麼要花力氣回答。

### 第四步：找口徑衝突

用鏡 6 掃一遍畫面本身。這一步不需要來源資訊，光看畫面就做得到，所以即使使用者手上只有原型也能給出價值。

### 第五步：排優先級輸出

見下面的輸出格式。

## 輸出格式

按嚴重度排序，不要按畫面順序排。使用者要的是「先處理哪個」，不是「第三張圖有什麼問題」。

分成三段：

```markdown
# 一、會讓功能做不出來的（來源決定）
逐項：問題 → 答錯的後果 → 誰決定

# 二、會算錯但不會報錯的（口徑決定）
逐項：現況 → 為什麼會錯 → 具體數字示範

# 三、實作細節
比較單純，工程可以自己決定的
```

最後收一張**檢查清單表格**：

| 優先 | 問題 | 性質 | 誰決定 |
|---|---|---|---|

優先級只有三檔：

- **必答**：答案會改變資料結構，或現在不問就補不回來
- **高**：會讓數字錯而且不會報錯
- **中／低**：影響查詢方式或畫面文案

---

## 寫作要求

**用具體數字示範，不要只講原則。**

「日均口徑跟區間口徑會不一樣」沒有說服力。這樣寫才有：

> 一個人 30 天天天來、只買一次。
> 區間口徑 = 買過的 1 人 ÷ 來過的 1 人 = **100%**
> 日均口徑 = 有買那天 100%、其餘 29 天 0%，平均 = **3.3%**
> 差 30 倍。

**每一個問題都要附「答錯會怎樣」。** 這是使用者拿去說服別人花時間回答的唯一籌碼。

**不要為了完整而完整。** 挑真正會出事的十幾項，講清楚。列三十項但每項兩行，對方會直接放棄。

**如果某一項你不確定成不成立，就說不確定，並說明怎麼驗證。** 儀表板需求分析最怕的是言之鑿鑿地講錯，因為對方會照著去改來源系統。

## 兩個常見情境的調整

**使用者手上只有一句話，還沒有原型**
先幫他列出典型元素，再挑其中最容易出事的三到五個深入。這時候鏡 6（口徑衝突）用不上，把力氣放在鏡 1（可加性）與鏡 3（時間歸屬），因為那兩個在還沒動工時最好改。

**使用者手上有完整原型或已上線的系統**
實際打開讀，找出畫面上已經存在的矛盾。這時候鏡 6 最有價值，因為那些矛盾是現成的證據，比任何推論都有說服力。已上線的系統還要多問一件事：**現在畫面上有沒有數字其實是錯的但沒人發現？**
